## 조사 범위와 확인된 사실

- 조사일: 2026-10-29. 현재 저장소의 apps/admin, packages, functions, docs 및 추적 파일을 검색했다.
- **참고 코드 확인:** 기존 랜딩은 Next.js + TypeScript 기반이며, 공통 스크립트를 app/layout.tsx의 next/script로 삽입하는 사례가 있다. mleverage.client.js SDK가 존재한다. 문의 성공 후 /complete?token=...으로 이동하고, 완료 페이지에서 sessionStorage 토큰으로 중복 실행을 줄이며 Google Ads·Meta Pixel 전환을 호출한 사례가 있다. Naver WCS 공통·전환 스크립트 사용 경험도 있다. 모두 사용자 제공 정보이며 원본 코드 미열람이다.
- **실제 저장소 코드 확인:** 이 저장소에는 Next.js 랜딩, 문의 폼, 운영 태그 스니펫, GTM 컨테이너 설정이 없다. 관리자 데모의 매체 설정은 광고 태그를 실행하지 않는다. tracking-sdk에는 설정 로더·라우트 감지·중복 시도 방지와 어댑터 인터페이스만 있고 매체 실행 어댑터는 없다.
- **운영 환경 검증 필요:** 제공된 사례가 현재 운영 랜딩에도 적용되는지, 정확한 설치 위치·문의 성공 조건·GTM 내부 태그·Naver WCS 버전·광고 플랫폼 수신 여부를 확인해야 한다.
- 아래 매체 표는 **현재 운영 랜딩의 설치 확인 결과**가 아니라 공식 자료와 제공된 참고 사례를 대조한 실행 기준이다.

## 매체별 공통·전환 실행 기준

| 매체 | 공통 실행 | 전환 실행 후보 | 실제 랜딩 확인 항목 |
|---|---|---|---|
| GTM | 컨테이너 로드, 기존 dataLayer 유지 | 문의 성공 후 dataLayer 이벤트를 전송하고 컨테이너 트리거 확인 | 컨테이너 ID, 내부 Ads/픽셀 태그, 트리거, 별도 하드코딩 여부 |
| Google Ads | Google tag 또는 GTM 안의 태그를 한 방식으로 구성 | 성공 시 해당 전환의 send_to 이벤트 | GTM 안팎 중복, AW ID·라벨, 전환 액션의 트리거 |
| Naver WCS | wcslog.js, 공통키, 유입 도메인, 페이지뷰 | 성공 시 전환 유형에 맞는 wcs.trans | 기존 wcs.cnv 사용 여부, 공통키·도메인·전환 유형, 페이지뷰 중복 |
| 당근 Pixel | 공통 전환 추적 코드 | 성공 행동에 맞는 이벤트 코드 | 설치 경로, 이벤트 유형, 광고주센터 이벤트 테스트 결과 |
| Meta Pixel | 픽셀 기본 코드 | 실제 성공 행동에 맞는 표준/맞춤 이벤트 | 픽셀 중복, GTM 설치 여부, 이벤트명과 테스트 이벤트 |
| TikTok Pixel | 사이트 전반의 기본 코드 | 이벤트 빌더 또는 맞춤 코드에서 선택한 이벤트 | GTM/직접 설치 중복, 이벤트 설정 방식, 테스트 이벤트 |

GTM의 dataLayer 이벤트가 태그를 실제로 발화시키는지는 컨테이너 트리거에 달려 있다. Google Ads는 공통 태그와 전환 이벤트를 분리한다. Naver WCS의 신형 wcs.trans와 구형 wcs.cnv를 같은 전환 지점에 함께 두면 중복될 수 있고, 신형 전환 테스트가 구형 로그 필터링에 영향을 줄 수 있으므로 실제 사이트에서 버전을 확인하기 전에는 교체 실험을 하지 않는다.

## 문의 완료 조건: 참고 사례와 목표 계약

**참고 코드 확인:** 문의 성공 후 /complete?token=...으로 이동한 사례가 있고, 완료 페이지에서 sessionStorage 토큰으로 중복 실행을 줄이며 Google Ads·Meta Pixel 전환을 호출한 사례가 있다. 원본 코드와 현재 운영 동작은 이 저장소에서 확인하지 못했다.

**실제 저장소 코드 확인:** 신규 SDK는 /complete?token 경로 감지와 sessionStorage 시도 키를 제공한다. 실제 문의 API, 완료 페이지, 매체 어댑터는 이 저장소에 없다. 기존 완료 페이지와 신규 SDK가 서로 다른 중복 키를 쓰면 두 경로가 모두 전환을 보낼 수 있으므로 토큰 중복 방지만으로 공존을 안전하다고 판단하지 않는다.

**운영 환경 검증 필요:** 목표 계약은 서버가 접수 성공을 확정한 뒤 고유 접수 식별자로 consultation_complete를 한 번 호출하는 것이다. /complete?token은 단기 호환 경로이며 token 자체는 접수 증명이 아니다. 실제 성공 응답, 리다이렉트 순서, 실패·중복 제출 동작을 확인해야 한다. 페이지 방문이나 버튼 클릭만으로 접수 성공을 판정하지 않는다.

실제 랜딩을 점검할 때 사이트별로 ① 문의 요청/성공 응답 위치 ② 완료 페이지 이동 방식 ③ 실패·중복 제출 처리 ④ 성공 식별자의 생성 위치 ⑤ 동의 상태를 기록한다. 운영 ID나 고객 정보는 이 문서에 적지 않는다.

## 기존 코드에서 신규 SDK로 이전하는 순서

1. 사이트별 app/layout.tsx의 next/script, 완료 페이지의 Google Ads·Meta 호출, mleverage.client.js의 역할, Naver 스니펫, GTM 컨테이너·호스팅 플러그인을 각각 대조한다. mleverage.client.js가 같은 전환을 보내는지는 확인 전까지 추정하지 않는다.
2. **siteId × 매체 × 이벤트**마다 단일 실행 주체를 정한다. 기존 코드, GTM, 기존 SDK, 신규 SDK 중 하나만 운영 전환을 보낸다. 신규 SDK의 로더와 어댑터를 추가할 때 기존 next/script 공통 태그와 완료 페이지 호출을 그대로 둔 채 같은 매체를 활성화하지 않는다.
3. 신규 SDK를 먼저 전환 어댑터 비활성 상태로 설치해 설정 조회·라우트 감지만 시험한다. 기존 태그가 살아 있는 동안 신규 SDK는 광고 태그 로드·전환을 실행하지 않는다. 이것은 향후 어댑터 배포 계획이며 현재 구현된 공존 토글은 아니다.
4. 테스트 환경에서 매체 하나씩 기존 공통 태그 및 완료 페이지 호출을 비활성화하고 신규 어댑터를 활성화한다. GTM 내부 태그가 있으면 해당 컨테이너 게시까지 같은 전환 계획에 포함한다. 중간 배포 상태에서 두 실행 주체가 동시에 켜지지 않도록 배포 순서를 기록한다.
5. /complete?token과 실제 문의 성공 이벤트가 같은 접수를 가리키는지 확인한다. 기존 sessionStorage 키와 신규 SDK 키는 독립적이므로 중복 방지의 근거로 삼지 않는다. 접수 성공 한 건당 매체별 전환 시도 한 건, 실패·새로고침·뒤로 가기에서 추가 시도 없음, 동의 거부 시 비실행을 검증한다.
6. 문제가 생기면 기존 태그 코드/컨테이너와 신규 게시 설정을 함께 이전의 단일 실행 주체 상태로 되돌린다. Naver WCS의 wcs.trans/cnv 전환은 기존 버전과 공식 가이드의 필터링 경고를 확인한 뒤 별도 절차로 진행한다.

## 포트폴리오 공개 전 이력 점검

현재 HEAD의 ID 형태 문자열은 가상 데이터와 입력 예시다. 하지만 초기 커밋 9908bfd의 관리자 파일에는 이전 업체 식별자 형태의 값이 남아 있다. 현재 저장소는 비공개이며, **Git 이력을 포함한 저장소를 그대로 공개하지 않는다.** 공개용으로는 별도의 깨끗한 이력/저장소를 만들고 전체 이력의 식별자 검사를 다시 수행한다. 기존 이력을 수정하거나 강제 푸시하지 않았다.
