## 작업 메모

- 구현 파일: `packages/tracking-sdk/src/index.ts`, `tests/sdk-conversion.test.mjs`, SDK 명세·아키텍처·테스트 문서.
- 사용자 확인: 기존 `mleverage.client.js` SDK는 문의·페이지뷰용이며 매체 픽셀을 담당하지 않는다. 픽셀 중복 점검 대상은 기존 `next/script`·완료 페이지 직접 호출·GTM 내부 태그와 신규 SDK 어댑터다.
- 전환 계약: 문의 성공 후 발급한 랜덤 token으로 `/complete?token=...`에 이동한다. SDK는 유효한 단일 token을 전환 식별자로 사용해 해당 경로에서 전환을 시도한다. `verifyCompletionToken`은 필요한 사이트에서 추가 검증을 적용할 수 있는 선택 옵션이다. token은 접수 사실을 스스로 증명하지 않으므로 랜딩은 성공 이후에만 완료 경로로 이동해야 한다.
- 중복 처리: siteId·전환 설정 ID·token의 해시를 `sessionStorage` 시도 키로 저장한다. 전환 설정 ID가 유지되면 게시 버전이 바뀌어도 같은 token은 같은 탭에서 재전송하지 않는다. 뒤로 가기·새로고침·재방문과 동시 호출도 막으며 저장소 사용이 불가능할 때는 탭 메모리로 대체한다. 전환 전 키를 기록하므로 전송 결과가 불명확한 경우 자동 재시도하지 않는다.
- 단일 실행 주체: 매체별로 기존 완료 페이지/GTM과 신규 SDK 중 한 곳에서만 전환을 보낸다. 기존 태그가 전환을 담당하는 매체는 신규 SDK에 해당 어댑터를 주입하지 않는다. 두 경로의 sessionStorage 키가 서로 다르면 SDK 내부 중복 방지만으로 교차 중복을 막을 수 없다.
- 테스트 결과: 관리자 데모 초안·게시 DTO가 SDK 공통 로더와 완료 경로 전환으로 이어지는 모의 통합 테스트를 추가했다. 실제 GTM·Google Ads 어댑터의 스크립트 삽입과 `/complete` 이벤트 큐를 모의 DOM에서 확인했다. 동일 token의 뒤로 가기·새로고침·게시 버전 변경, 독립 새 탭 세션, 저장소 접근 실패, 스크립트 로드 실패·전환 오류도 확인했다. 전체 `npm test` 57건, `npm run typecheck`, `npm run build` 통과.
- 남은 이슈: 관리자 화면의 게시본은 브라우저 메모리 데모라 SDK 공개 설정 API와 연결되지 않았다. 로컬 관리자 UI 직접 검증은 브라우저 자동화 도구가 현재 URL을 확인하지 못해 수행하지 못했으며, 위 통합 검증은 데이터 처리 함수와 모의 DOM 기준이다. 실제 랜딩의 스크립트 네트워크 로드, 기존 완료 페이지 호출 제거, GTM 내부 태그, 광고 플랫폼 수신을 운영 환경에서 확인해야 한다. [MDN의 sessionStorage 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)처럼 저장소는 탭별이고 opener가 있는 새 탭에는 초기 값이 복사될 수 있다. 독립 새 탭에서 같은 URL을 열면 다시 시도할 수 있으며, token 해시는 전송 완료 증명이 아니라 브라우저 시도 기록이다.
