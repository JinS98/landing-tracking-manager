# 시스템 아키텍처

## 경계

    회사 VPN/프록시/기존 인증 게이트
                 |
          관리자 API (미구현) ── Firestore 초안/릴리스/감사 로그
                 |                       |
          React 관리자 UI           게시 작업 (미구현)
                                         |
                                  공개 JSON/CDN (미구현)
                                         |
    신규 랜딩 ── 독립 Tracking SDK ── 게시 설정만 조회

관리자 앱은 화면과 입력 경험을 담당합니다. 현재는 메모리 데모 상태만 있습니다. adminGateway.ts는 나중에 서버를 연결할 인터페이스이며, 브라우저가 권한을 판정하거나 Firestore를 직접 쓰지 않습니다. functions/src/access.ts는 서버의 게이트 검증과 인가를 분리한 계약입니다.

tracking-core는 공개 설정의 허용 필드·타입을 검증합니다. tracking-sdk는 설정 로드, 라우트 감지, 중복 방지와 어댑터 호출을 담당합니다. 매체별 실행 어댑터는 별도 검증 후 추가합니다. **참고 코드 확인:** 기존 랜딩에는 mleverage.client.js가 존재한다는 사용자 제공 사례가 있습니다. 이 SDK가 어떤 태그나 전환을 실행하는지는 원본 코드·운영 환경 검증 전까지 확정하지 않습니다. 신규 SDK는 별도 모듈로 유지하며 중복 실행 경계를 검증합니다.

## 운영 요청 흐름

1. 사내 게이트가 직원 접근을 허용하고 서버에 신뢰 가능한 운영자 컨텍스트를 전달한다.
2. 서버가 매 요청에서 신원·권한·사이트 범위와 CSRF/세션 조건을 확인한다.
3. 서버가 siteId 기준으로 초안 버전을 비교해 Firestore에 쓰고 auditLogs를 기록한다.
4. 게시 시 불변 trackingReleases를 생성하고 공개 필드만 정적 JSON으로 내보낸다.
5. CDN 캐시 갱신 후 SDK는 게시본만 읽는다. 롤백은 이전 내용을 새 버전으로 다시 게시한다.

이 흐름은 설계이며 현재 서버 구현이 아닙니다.

## 기존 랜딩에서 신규 SDK로 이전

**참고 코드 확인:** Next.js + TypeScript 랜딩의 app/layout.tsx에서 next/script로 공통 스크립트를 삽입하고, 문의 성공 뒤 /complete?token으로 이동해 완료 페이지에서 sessionStorage 중복 방지와 Google Ads·Meta Pixel 전환 호출을 사용한 사례가 있습니다. Naver WCS 공통·전환 사용 경험도 있습니다. 이 정보는 사용자 제공 사례이며 현재 저장소에서 직접 확인한 운영 코드가 아닙니다.

**실제 저장소 코드 확인:** 신규 tracking-sdk에는 공개 설정 로더·History 이동 감지·/complete?token 감지·sessionStorage 시도 키가 있지만, 매체 실행 어댑터는 없습니다. 기존 완료 페이지와 신규 SDK가 서로 다른 키를 쓰면 두 경로 모두 전환을 보낼 수 있습니다. 키 존재 여부만으로 중복 실행을 차단했다고 판단하지 않습니다.

이전 순서는 다음과 같습니다.

1. app/layout.tsx, 완료 페이지, mleverage.client.js, Naver 스니펫, GTM 컨테이너·플러그인의 실제 역할을 사이트별로 대조한다. GTM 내부 설정과 Naver WCS 호출 버전은 **운영 환경 검증 필요**다.
2. siteId·매체·이벤트마다 전환의 단일 실행 주체를 기존 코드/GTM/기존 SDK/신규 SDK 중 하나로 정한다. 공통 로더와 전환 호출을 각각 기록한다.
3. 신규 SDK를 매체 어댑터 비활성 상태로 설치해 설정 로드와 라우트 감지만 검증한다. 기존 next/script 공통 태그와 완료 페이지 전환은 이 단계에서 유지한다. 현재 코드에는 운영용 공존 토글이 없으므로 구현 후 적용한다.
4. 테스트 환경에서 매체 하나씩 기존 공통 태그·전환 호출을 비활성화하고 신규 어댑터를 활성화한다. GTM 내부 태그가 있으면 컨테이너 게시도 같은 변경 묶음으로 관리한다. 두 실행 주체를 동시에 활성화하지 않는다.
5. 실제 성공·실패·재방문·뒤로 가기·SPA 이동·동의 거부를 시험하고 매체별 네트워크 전송 및 플랫폼 테스트 이벤트를 확인한다. 수신 결과는 **운영 환경 검증 필요**다.
6. 롤백은 랜딩 코드/컨테이너와 신규 게시 설정을 함께 이전의 단일 실행 주체 상태로 되돌린다. Naver WCS의 trans/cnv 버전 전환은 별도 검토한다.

사이트별 기록 양식은 [1일차 문서](daily/day-01.md)에 있습니다.

## 실패 경계

설정 로드나 외부 태그 실패는 문의 폼을 막지 않아야 합니다. SDK는 제한된 fetch 재시도만 하며 전환 전송을 자동 재시도하지 않습니다. 접근 게이트 미연결 상태에서는 운영 관리자 API를 배포하지 않습니다.
