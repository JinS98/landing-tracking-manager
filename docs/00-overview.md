# 프로젝트 개요

## 목적과 범위

신규 광고주 랜딩에 독립형 Tracking SDK를 적용하고, 사내 직원이 로그인 화면 없이 업체를 선택해 광고 설정을 관리하는 MVP를 목표로 합니다. 추후 회사 관리자 시스템의 인증·권한·접근 프록시에 연결합니다. 공개 포트폴리오 시연에는 가상 업체와 가상 ID만 사용합니다.

## 현재 구현

- 관리자: 가상 업체/다중 사이트 검색·선택, siteId 중복 방지 데모 등록, `.xlsx` 일괄 등록 미리보기·메모리 importJobs, 6개 매체 설정 편집, 초안/데모 게시/롤백/이력, 대시보드
- 공통 패키지: 초안·공개 게시 설정 타입, 매체별 입력 검증, 공개 DTO 투영
- SDK: 게시 설정 fetch, 제한된 재시도, 중복 시도 방지, Next.js식 History 이동 감지, 랜덤 token 기반 /complete 전환 감지, 어댑터 주입 인터페이스와 선택적 6개 매체 어댑터. 실제 랜딩 검증은 미완료
- 서버/CLI: 사이트 등록 Firestore 트랜잭션, 독립 공개 설정 HTTP 핸들러·Firestore 리더, 배포 CLI는 로컬 검증됨. 관리자 게시 쓰기·일괄 등록 서버 API·CDN·실제 진단은 미구현

데모 게시본은 브라우저 메모리에서만 유지되고 공개 HTTP 핸들러로 제공되지 않습니다. 핸들러는 서버의 Firestore 게시 포인터와 릴리스를 읽도록 구현됐으며 미배포 상태입니다. 화면의 SDK 상태는 가상 값이며 실제 설치 확인이 아닙니다.

## 개발 단계

1. 사내 태그 사용 현황과 중복 제거 계획 확인 (1일차: 참고 사례와 현재 저장소 코드 구분 완료, 운영 랜딩/GTM 증거 검증 필요)
2. 접근 게이트 및 서버 API 계약·Firestore Rules 확정
3. 사이트 등록 CLI와 Firestore 저장 구현
4. 6개 매체 어댑터와 실제 랜딩 통합 시험
5. 게시 JSON/CDN·롤백·진단·운영 검증

## 제외

MVP 로그인 UI, 직원별 업체 권한 관리 UI, 임의 JavaScript 실행, MLeverage SDK 수정, 광고 플랫폼 집계 보장은 범위에 넣지 않습니다.

## 기존 랜딩 정보의 상태

| 상태 | 내용 |
|---|---|
| 참고 코드 확인 | 사용자 제공 사례: Next.js + TypeScript 랜딩, app/layout.tsx의 next/script 공통 태그, 문의·페이지뷰용 mleverage.client.js(사용자 확인), /complete?token 이동, 완료 페이지의 sessionStorage 중복 방지 및 Google Ads·Meta 전환 호출, Naver WCS 사용 경험. 원본 코드는 이번 작업에서 열지 않았다. |

| 운영 환경 검증 필요 | 현재 운영 랜딩의 설치 경로와 문의 성공 조건, GTM 내부 태그·트리거, Naver WCS 호출 버전, 광고 플랫폼 수신 결과. |
