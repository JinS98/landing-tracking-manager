# 프로젝트 개요

## 목적과 범위

신규 광고주 랜딩에 독립형 Tracking SDK를 적용하고, Firebase Google 로그인으로 제한된 관리자가 업체별 광고 설정을 관리하는 MVP를 목표로 합니다. 공개 포트폴리오 시연에는 가상 업체와 가상 ID만 사용합니다.

## 현재 구현

- 관리자: 업체/다중 사이트 검색·선택, siteId 중복 방지 등록, `.xlsx` 일괄 등록, 6개 매체 설정 편집, 초안 저장·게시·롤백·이력, 대시보드. 로컬 데모 모드와 운영 Firebase 로그인·API 모드를 분리
- 공통 패키지: 초안·공개 게시 설정 타입, 매체별 입력 검증, 공개 DTO 투영
- SDK: 게시 설정 fetch, 제한된 재시도, 중복 시도 방지, Next.js식 History 이동 감지, 랜덤 token 기반 /complete 전환 감지, 어댑터 주입 인터페이스와 선택적 6개 매체 어댑터. 실제 랜딩 검증은 미완료
- 서버/CLI: Firebase ID 토큰과 관리자 계정 확인, 업체·사이트·일괄 등록 API, 초안·게시·롤백 Firestore 트랜잭션, 독립 공개 설정 및 진단 HTTP 함수. 배포 CLI의 실제 자격 증명 연동은 미구현

로컬 데모 게시본은 브라우저 메모리에만 유지됩니다. 운영 게시본은 Firestore의 게시 포인터와 릴리스에서 공개 HTTP 핸들러가 읽습니다. SDK 상태는 실제 사이트 설치 확인 전까지 추정값일 수 있습니다.

20일차 정적 데모 배포 후 2026-11-03에 https://pixel-manager.web.app 의 관리자 화면과 SDK 번들, Firebase Auth·Firestore Rules·Functions를 라이브로 전환했습니다. 비로그인 차단과 공개 URL 응답은 확인했으며 실제 계정 로그인·게시와 광고 플랫폼 수신은 아직 검증하지 않았습니다. `landing-tracking.web.app`은 전역 이름 충돌로 사용할 수 없었습니다. 자세한 범위와 복구 절차는 [배포 문서](07-deployment.md)에 있습니다.

## 개발 단계

1. 사내 태그 사용 현황과 중복 제거 계획 확인 (1일차: 참고 사례와 현재 저장소 코드 구분 완료, 운영 랜딩/GTM 증거 검증 필요)
2. 접근 게이트 및 서버 API 계약·Firestore Rules 확정
3. 사이트 등록 CLI와 Firestore 저장 구현
4. 6개 매체 어댑터와 실제 랜딩 통합 시험
5. 게시 JSON/CDN·롤백·진단·운영 검증

## 기존 랜딩 정보의 상태

| 상태 | 내용 |
|---|---|
| 참고 코드 확인 | 사용자 제공 사례: Next.js + TypeScript 랜딩, app/layout.tsx의 next/script 공통 태그, 문의·페이지뷰용 mleverage.client.js(사용자 확인), /complete?token 이동, 완료 페이지의 sessionStorage 중복 방지 및 Google Ads·Meta 전환 호출, Naver WCS 사용 경험. 원본 코드는 이번 작업에서 열지 않았다. |
| 실제 저장소 코드 확인 | 이 저장소의 관리자 데모·tracking-core·tracking-sdk와 6개 매체 어댑터 소스를 직접 확인했다. 실제 랜딩과 완료 페이지는 포함되지 않는다. |
| 운영 환경 검증 필요 | 현재 운영 랜딩의 설치 경로와 문의 성공 조건, GTM 내부 태그·트리거, Naver WCS 호출 버전, 광고 플랫폼 수신 결과. |

기존 랜딩의 태그 위치와 문의 성공 조건을 운영 코드와 대조하기 전에는 태그 교체를 완료로 표시하지 않습니다. 상세 조사표와 중복 실행을 막는 이전 순서는 [1일차 기록](daily/day-01.md)에 있습니다.
